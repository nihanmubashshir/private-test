# US-010 — Workout library and gym plans

## 1. User story

> **As** someone who trains on a weekly split that changes every few months,
> **I want** to define my regular exercises once, build several weekly plans from them, and mark one
> as active,
> **so that** when I get to the gym the app already knows what today's session is, and switching
> blocks is one tap rather than a rebuild.

## 2. Data

`supabase/migrations/20260913113320_gym_plans.sql`. Four tables plus an enum.

| Table | Notes |
|-------|-------|
| `workouts` | `tracks tracked_field[]` — what a set records. An array, not four booleans, so US-011's set logger is generated by iterating it in a fixed order |
| `plans` | `is_active` |
| `plan_days` | Exactly 7 per plan, `weekday` 0 = Monday (ISO) |
| `plan_items` | An exercise in a day, with optional targets |

**Three invariants live in the database, because application code cannot promise them:**

1. `create unique index plans_single_active on plans (owner_id) where is_active` — two concurrent
   activations cannot both succeed.
2. `create unique index workouts_owner_name on workouts (owner_id, lower(name))` — case-insensitive
   uniqueness that does not depend on a query-then-insert racing with itself. The action learns
   about collisions from the `23505` Postgres raises.
3. `create_plan()` inserts the plan **and all seven rest days** in one call, so no read ever has to
   cope with a plan that has fewer than seven days.

`activate_plan()` is an RPC rather than two updates in the action: the partial unique index rejects
a second active plan, so clearing and setting must not be observable apart.

`weekdayFromDate()` converts `Date`'s Sunday-first `getDay()` to the Monday-first `weekday` the week
strip reads in — in one place, so the off-by-one cannot spread.

### 2.1 Seeding

`seed_gym_defaults()` is a **function the app calls**, not `INSERT`s in the migration. Every row is
owner-scoped via `auth.uid()` and a migration runs with no auth context, so plain inserts would
write rows owned by nobody — invisible under RLS and impossible to delete from the app. It no-ops
once the owner has any workout, so calling it on every visit to a gym screen is safe.

## 3. Screens

| Route | What |
|-------|------|
| `/gym/plans` | Active plan card, other plans, New plan (optionally a copy of an existing one) |
| `/gym/plans/[id]` | Week strip, day name, rest toggle, exercise list, picker, targets |
| `/gym/workouts` | Searchable library, create/edit sheet, archived section |

Home gets a Gym card reading **only the active plan**; a matching day in an inactive plan changes
nothing. A rest day renders as a quiet row, not a card, so it does not look like something to act
on. Settings gets Plans and Exercises rows.

Every edit in the plan editor **saves immediately** — no Save button, no dirty state. A weekly plan
is a list of small independent facts, not a form with a single commit.

## 5. Acceptance criteria

1. Creating an exercise with `tracks: ['reps']` will produce a reps-only set logger in US-011.
2. A duplicate exercise name is rejected case-insensitively with an inline error.
3. An exercise cannot be added twice to the same day; it shows disabled with "Added".
4. Reordering persists across a reload.
5. Toggling a day to Rest hides it from Home but keeps its exercises when toggled back.
6. Creating a plan "from" another copies all seven days, names, rest flags, items, positions and
   targets, and the copy is **not** active.
7. Archiving is offered instead of deleting; an archived exercise leaves existing plans intact.
8. On a non-rest day of the **active** plan, Home shows that day with the right exercise count. A
   matching day in an inactive plan changes nothing.
9. At most one plan is active, enforced by the database index.
10. Deleting the active plan is refused with a message naming the fix.
11. At 320px the week strip scrolls horizontally and nothing else overflows.
12. Every row and control is at least 44px tall.

## 6. Deviations

| # | What changed | Why |
|---|--------------|-----|
| D1 | Reordering is **up/down buttons, not drag** | A drag handle competes with the week strip's horizontal scroll and the page's vertical scroll, and loses to both on a phone. Buttons also give a 44px target and a keyboard path for free. |
| D2 | No swipe-to-remove | Same gesture conflict; remove is an explicit button. |
| D3 | Seeding is a function, not migration `INSERT`s | §2.1 — owner-scoped rows need an auth context. |
| D4 | "Copy from another day" within one plan is not built | "Start from: copy of an existing plan" covers the A/B-split case it was for, at the plan level. Revisit if editing proves tedious. |
| D5 | The day-name field commits on **blur**, not on change | Controlled with `onChange` it fired a Server Action per keystroke — one write per character. |
| D6 | `pnpm db verify` not run | `SUPABASE_DB_URL` is empty in `.env.local`; see US-008 D3. |
